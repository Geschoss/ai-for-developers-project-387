Разработайте совместно с ИИ сервис для бронирования календаря

Учебный проект Хекслета: https://ru.hexlet.io/programs/ai-for-developers

## Стек

- API-контракт: TypeSpec → OpenAPI
- Бэкенд: NestJS, TypeScript, Drizzle, PostgreSQL
- Фронтенд: React, TypeScript, Vite, Mantine
- Тесты: Vitest, Testcontainers, Playwright
- Развёртывание: Docker, GitHub Actions, Render

## Установка

Нужны [mise](https://mise.jdx.dev/) (ставит Node и pnpm нужных версий из `mise.toml`) и Docker.

```bash
git clone https://github.com/Geschoss/ai-for-developers-project-387.git
cd ai-for-developers-project-387
mise install
pnpm install
```

`mise install` ставит git-хук pre-commit. Хук проверяет oxlint и формат только у файлов в индексе и ничего не исправляет.

Запуск всего приложения с базой — в Docker, на http://localhost:3000:

```bash
ADMIN_EMAIL=admin@example.com ADMIN_PASSWORD=придумайте-пароль docker compose up --build
```

Режим разработки: база в Docker, бэкенд и фронтенд с перезагрузкой, фронтенд на http://localhost:5173:

```bash
docker compose up -d db
cp .env.example backend/.env  # замените ADMIN_PASSWORD на свой
pnpm dev
```

### Администратор

Администратор один. Его создаёт старт приложения из переменных окружения `ADMIN_EMAIL` и `ADMIN_PASSWORD`, если
в базе Администратора ещё нет. Повторный старт второго не создаёт, даже если переменные изменились: пароль
существующего Администратора они тоже не меняют. Без любой из двух переменных приложение не стартует и пишет,
какой не хватает (`ADMIN_EMAIL is not set`). Если `ADMIN_EMAIL` уже занят Владельцем, старт тоже падает с ошибкой.

Учётные данные не коммитьте: в `.env.example` только заглушки. На проде задайте их в переменных окружения сервиса.

Публичный адрес: https://ai-for-developers-project-387-icuo.onrender.com. На Render работают web service из
`Dockerfile` и Postgres, оба на бесплатном плане. Бесплатный Postgres живёт 30 дней. `ADMIN_EMAIL` и `ADMIN_PASSWORD`
задаются в переменных окружения сервиса в панели Render и в репозиторий не попадают.

На прод уходят только релизы. Когда релизный PR (`chore(main): release …`) смержен и `ci` на его коммите в `main`
зелёный, job `deploy` в `ci.yml` вызывает Deploy Hook сервиса с этим коммитом. Обычные PR в `main` не деплоятся.
Настройка один раз: в панели сервиса Settings → Auto-Deploy → Off, затем скопировать Deploy Hook из Settings и
сохранить его секретом репозитория командой `gh secret set RENDER_DEPLOY_HOOK_URL`. URL хука сам запускает деплой,
не коммитьте его.

### Render MCP

Подключение Cursor к Render. Файл `.cursor/mcp.json` берёт ключ из окружения (`RENDER_API_KEY`) и не содержит сам ключ.

1. Создайте ключ: https://dashboard.render.com/u/settings#api-keys
2. Экспортируйте его в окружение как `RENDER_API_KEY`. Ключ не коммитьте.
3. Перезапустите Cursor.
4. Проверьте подключение: запросите список сервисов Render.

Проверки качества кода: `mise run check` (oxlint, oxfmt, tsc, knip, dependency-cruiser, сверка контракта, shell-тесты бюджета агента `scripts`, тесты и e2e, по очереди). По отдельности: `mise run lint`, `format`, `fix`, `typecheck`, `knip`, `depcruise`, `spec`, `scripts`, `test`, `e2e`. Тестам нужен запущенный Docker. Браузер Playwright ставится один раз: `pnpm --filter e2e exec playwright install chromium`.

`.github/workflows/opencode.yml`.

Разрешены чтение репозитория, `gh issue`, `gh label`, `gh api` этого репозитория и каталог конфига `gh`. Используется стандартный режим: [GitHub App OpenCode](https://github.com/apps/opencode-agent), установленный на

получает чтение кода и запись в issues (для `gh`), но не запись кода и не PR. Пример: `/oc explain this issue`.

Настройки агент читает из `docs/agents/`: трекер задач (GitHub issues через `gh`), метки триажа и доменные документы (`GLOSSARY.md`, `docs/adr/`, `docs/spec.md`). Ему доступны скиллы из `.agents/skills/`, а все проверки проекта запускаются командой `mise run check`.

### Предел запусков на PR

Один PR получает не больше **3** допущенных запусков агента. Бюджет проверяет код до вызова модели: в
`.github/workflows/opencode.yml` задание `budget` (без модели и секрета) запускает `scripts/oc-budget.sh count`, а
задание `opencode` стартует только при `allowed=true`.

| Что            | Значение                                                                                                                                                                                                                 |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Что считается  | Каждый допущенный запрос человека: общий комментарий и комментарий к строке. Отмена, тайм-аут, упавший запуск и повторная попытка (Re-run, `run_attempt`) тоже тратят попытку. Отказ по бюджету не тратит                |
| Откуда счётчик | История Actions: задания `opencode` этого воркфлоу, не пропущенные (`skipped`). Токен получает `actions: read` и переписать историю не может. Комментарий PR только отчёт и бюджет не меняет                             |
| Связь с PR     | `run-name: opencode #<номер>`: номер берётся из события, текст комментария на имя не влияет                                                                                                                              |
| Где лимит      | Только на PR. На обычном issue лимита нет: из него запускается `implement-spec`. Новый PR получает новый бюджет                                                                                                          |
| При исчерпании | Модель не вызывается. Задание `report` пишет комментарий: причина `limit_exhausted`, последний SHA PR, ссылка на лог, «нужен человек»                                                                                    |
| Причины сбоя   | `report` (без модели, `if: always()`) пишет `timeout` (задание дошло до 60 минут), `infra` (нет секрета, упал шаг подготовки), `agent_failed` (упал шаг `Run OpenCode`). Иначе `unknown`: смотрите лог                   |
| Права `report` | `contents: read`, `actions: read`, `issues: write`, `pull-requests: write`. Запись в PR нужна только для комментария: с `issues: write` и `pull-requests: read` GitHub отвечает 403. Ни модели, ни секрета в задании нет |
| Тесты          | `scripts/oc-budget.test.sh` с подставным `gh`, входит в `mise run check`                                                                                                                                                 |

Как проверить предел вручную: откройте любой PR из этого репозитория и три раза напишите `/oc` с коротким вопросом,
дождавшись ответа каждый раз. Четвёртая команда не вызывает модель: задание `opencode` пропущено, а `report` оставляет
комментарий с причиной `limit_exhausted`, последним SHA и ссылкой на лог.
Пример: четвёртая команда на PR #39, [прогон](https://github.com/Geschoss/ai-for-developers-project-387/actions/runs/42637390324): модель не вызывалась, комментарий опубликован.

Ограничения: счёт верен при сохранённой истории Actions и неизменном воркфлоу, администратор репозитория может изменить
обе вещи. Два комментария, отправленные в одну секунду, оба увидят прежний счёт, и бюджет может превысить одна
попытка. Следующее действие выбирает человек, цикл исправлений не автоматический.

Тикеты и спецификации нужно создавать сразу с меткой (`gh issue create --label …`): воркфлоу читает метки в момент
`opened`. Воркфлоу запускается из ветки по умолчанию, поэтому изменения вступают в силу после слияния в `main`.

### Авторевью PR

Воркфлоу `.github/workflows/opencode-review.yml` проверяет каждый PR отдельным запуском, не связанным с сессией
реализации. Ревьюер читает diff, описание PR, спецификацию и тикеты по ссылкам, результаты CI и оставляет
комментарий. Код он не правит: подтверждённое замечание автору передаёт человек командой `/oc`.

| Что               | Значение                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Событие           | `pull_request`: `opened`, `synchronize`, `reopened`, `ready_for_review`. Это отдельное событие от `/oc`-комментариев                                                                                                                                                                                                                                                                                                       |
| Чьи PR            | Из этого же репозитория (fork без секрета модели), не черновики, не release-PR. Автор `OWNER`, `MEMBER`, `COLLABORATOR` или `opencode-agent[bot]` по точному логину                                                                                                                                                                                                                                                        |
| Как работает      | Обычный OpenCode CLI (`opencode run`), не `opencode github run`: тот проверяет права отправителя и для PR от App отвечает `permission: none`. Доверие проверяет само условие `if`                                                                                                                                                                                                                                          |
| Где работает      | Рабочий каталог ревьюера это основная ветка: конфиг OpenCode, плагины, `AGENTS.md`, спецификацию и `REVIEW.md` он берёт оттуда. Код PR (`pull_request.head.sha`, не merge-коммит) читается только через `git diff` и `git show`, поэтому PR не подменяет правила и не исполняет свой код рядом с секретом. Пока `REVIEW.md` и `.github/opencode-review.json` нет в основной ветке (первый PR с ними), берутся версии из PR |
| Критерии          | `REVIEW.md`. Передаётся ревьюеру файлом (`--file`) и упоминается в запросе. Если PR меняет сами правила, ревьюер отмечает это отдельным риском                                                                                                                                                                                                                                                                             |
| Какой коммит      | SHA проверенного `head` указан в заголовке комментария                                                                                                                                                                                                                                                                                                                                                                     |
| Права             | Задание `review`: только чтение (`contents`, `issues`, `actions`, `checks`, `statuses`, `pull-requests`). Запись в PR только у задания `publish`, у которого нет модели и секрета                                                                                                                                                                                                                                          |
| Разрешения агента | `.github/opencode-review.json` на время ревью подменяет `opencode.json` в рабочем каталоге (`OPENCODE_CONFIG` проектный файл не перекрывает): правка файлов запрещена, разрешены чтение репозитория, `git diff/show`, `gh pr view/diff/checks`, `gh run view/list`, `gh issue view/list`                                                                                                                                   |
| Тайм-аут и отмена | 10 минут на ревью, 5 на публикацию. `concurrency` с `cancel-in-progress: true` на номер PR: устаревшее ревью отменяется новым пушем                                                                                                                                                                                                                                                                                        |
| Результат         | Новый комментарий «Авторевью» с SHA и ссылкой на прогон. Сбой публикуется тем же заданием без модели: `infra`, `agent_failed` или `timeout`, статус «нужен человек»                                                                                                                                                                                                                                                        |
| Шаблон PR         | `.github/pull_request_template.md`: `Closes #`, Summary, «Проверки», «Риск», «Откат». Правила заполнения: `docs/agents/pull-requests.md`                                                                                                                                                                                                                                                                                   |

Ограничение: для события `pull_request` GitHub берёт файл воркфлоу из самого PR, поэтому PR из этого репозитория может
изменить воркфлоу, получающий секрет. Фильтр автора лежит в том же файле. Любое изменение `.github/workflows/` проходит
отдельное решение человека (критерий 10 `REVIEW.md`).

Комментарий ревью не запускает правку. Бот не вызывает `/oc`: воркфлоу агента пропускает комментарии ботов. Если ревью
не стартовало, проверьте источник токена автора PR и ожидающее подтверждение запуска во вкладке PR.

### Проверка работающей версии PR

Задание `verify-head` в `.github/workflows/ci.yml` на событии `pull_request` собирает приложение из **точного head PR**
(`pull_request.head.sha`, не временный merge-коммит) и проходит в браузере основной и соседний сценарии: Бронирование
Гостя видно Владельцу (`events.spec.ts`) и второй Гость не занимает тот же Слот (`booking.spec.ts`). Секрета модели в
задании нет. Для успешных прогонов trace включён явно: `E2E_TRACE=on` в `e2e/playwright.config.ts`.

Артефакт Actions `head-verification-<sha>` содержит `sha.txt` (результат `git rev-parse HEAD`), `verdict.json`
(`pass` только если выполнены оба сценария, `expected: 2`, `skipped: 0`; иначе `fail`; SHA, ссылка на прогон), отчёт Playwright и trace каждого теста (`e2e/test-results/**/trace.zip`,
открывается `pnpm --filter e2e exec playwright show-trace <путь к trace.zip>`), скриншоты каждой страницы теста (`test-finished-*.png`). Перед мержем:

1. Откройте артефакт в прогоне `ci` этого PR и сверьте `sha.txt` с текущим head PR (`gh pr view <n> --json headRefOid`).
2. Убедитесь, что `verdict.json` содержит `"result": "pass"`, и откройте trace.
3. После нового push старый артефакт остаётся свидетельством прежней версии: проверку нужно повторить. Авторевью,
   запущенное параллельно с CI, артефакт может ещё не видеть.

### Защита основной ветки

Мерж в `main` требует успешного `ci`, одобрения ревьюеров не требуются (единственный владелец).
Включается в Settings → Rules → Rulesets (или Branches → Branch protection rule): _Require status checks to pass_ с
проверкой `ci`. Заголовок PR CI не проверяет: перед squash-мержем посмотрите его в окне мержа (формат: `docs/agents/pull-requests.md`). Если тариф не позволяет, перед мержем вручную проверьте статусы PR
(`gh pr checks <n>`) и зафиксируйте это в комментарии.

### Аудит скорости

Воркфлоу `.github/workflows/audit.yml` раз в сутки и по кнопке (Actions → audit → Run workflow) замеряет работающее
приложение Lighthouse, сохраняет отчёт артефактом, а агент OpenCode заводит отдельный issue по каждой новой находке.

| Что                | Значение                                                                                                                                                                                                                                                                                  |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| События            | `schedule`: `17 6 * * *` с `timezone: Europe/Moscow` (раз в сутки, 06:17 по Москве; GitHub может задержать или пропустить запуск, а в публичном репозитории отключает расписание через 60 дней без активности) и `workflow_dispatch` с входом `training`. Файл должен лежать в `main`     |
| Адрес              | Переменная репозитория `APP_URL` (Settings → Variables → Actions). ## Использование

Сервис для трёх ролей. Владелец регистрируется сам, Гость бронирует по ссылке без аккаунта, Администратор
только смотрит список Владельцев.

### Демо-календарь

На чистой базе старт создаёт Владельца «Демо», если его email и Адрес календаря ещё свободны. Пояс
`Europe/Moscow`, горизонт 14 дней. Повторный старт учётку не перезаписывает и пароль не меняет. Если email
или Адрес уже заняты, старт не падает и второго такого Владельца не создаёт.

- Адрес календаря: `demo`, страница `/u/demo`
- На проде: https://ai-for-developers-project-387-icuo.onrender.com/u/demo
- Вход: `demo@example.com`, пароль `demo-owner-1`
- Тип события: «Звонок», описание «Короткий созвон на 30 минут», 30 минут

Проверка: откройте ссылку без входа, выберите «Звонок» и забронируйте свободный Слот. Затем войдите
демо-учёткой. Бронирование видно в «Предстоящих событиях».

### Владелец

1. Откройте сайт и нажмите «Регистрация». Укажите имя, email, пароль, Адрес календаря
   (`a-z`, цифры и дефис, 3–30 символов) и часовой пояс.
2. После регистрации открываются «Предстоящие события». Пока Бронирований нет, список пуст.
3. В «Настройках» меняются часовой пояс, Горизонт планирования (1–60 дней, по умолчанию 14) и Лимит
   бронирований (1–18 на email за день, по умолчанию 2). Уже сделанные Бронирования при этом остаются.
4. «Скопировать ссылку» кладёт в буфер адрес текущего сайта: `/u/<адрес-календаря>`. Его и отправляют
   Гостю. «Мой календарь» открывает ту же страницу.
5. Когда Гость бронирует Слот, в «Предстоящих событиях» появляются его имя, email, время Слота в поясе
   Владельца и дата создания. Список идёт по времени начала. Слот, который уже начался, пропадает.

### Гость

1. Откройте ссылку Владельца, `/u/<адрес-календаря>`.
2. Выберите день в пределах горизонта и свободный Слот. Время показано в поясе браузера. Если он не
   совпадает с поясом Владельца, на странице есть плашка с временем Владельца.
3. Введите имя и email и нажмите «Забронировать». Аккаунт не нужен, письма не отправляются.
4. Экран «Вы записаны» показывает Владельца, дату и время в обоих поясах.
5. Занятый Слот второй Гость занять не может. Нельзя бронировать прошедший Слот, Слот за горизонтом и
   свой собственный календарь. Один email не может превысить Лимит бронирований за день в поясе Владельца.

### Администратор

1. Войдите email и паролем из `ADMIN_EMAIL` и `ADMIN_PASSWORD`. Регистрация Администратора не создаёт.
2. Открывается список Владельцев: имя, email, ссылка на календарь, часовой пояс и дата регистрации.
   Календаря у Администратора нет, и предстоящие Бронирования ему не показываются.
